# MRN 触摸与按键接口

适用范围见 [MRN 设备说明](../mrn.md)。本页记录 F3.21 原厂驱动的已恢复行为及当前桥接采用的接口，不是整车 CAN DBC。原厂行为依据模块指令、注册配置及局部 ARM 执行核对；局部执行中的 OS、时钟和硬件由替身提供。

## 原厂输入链路

| 输入 | 原厂路径 | 对适配的含义 |
| --- | --- | --- |
| 触摸 | `CAN1:` → `CANSDK.dll` → `entHmiTouchScreenDriver.dll` / `TSD1:` → `MQ_INFO_TACTILE` → 原厂窗口 | 驱动向缓存的目标 HWND 投递鼠标消息，不跟随当前前台窗口 |
| 面板/方向盘 | ICC → `ssw_IPCDispatcher.dll` / `IPC1:` → HMI 输入转换 | 原始输入编号、HMI 语义事件、标准虚拟键是不同编号空间 |
| 车辆状态 | `ICC0:` → `entRMIDrvr.dll` / `RMI1:` → `entRMIAccessLib.dll` | RMI 消息与 IE 编号不是车辆 CAN 仲裁 ID |

触摸驱动按固定标题 `DPCA_HMI_WINEA7:0` 查找原厂窗口。仅调用 SetForegroundWindow 或创建置顶窗口，不能使 WinXPlay 自动收到物理触摸。

`CAN_Open` 返回共享设备上下文，邮箱事件和收发锁也是设备级资源；接口没有为每次打开建立报文副本。`MQ_INFO_TACTILE` 是原厂消费者队列。因此当前接收端既不增加 CAN 收包者，也不增加该队列的读者，避免竞争消费。此结论限定于已分析的接口，不等同于硬件绝无多邮箱能力。

## 坐标和事件语义

原厂触摸帧为 CAN1 标准 ID `0x00F`、DLC 7。以下 D0…D6 指总线字节顺序；驱动缓冲前八字节按 `D3 D2 D1 D0 D7 D6 D5 D4` 排列，不能直接套用总线公式读取内存。

```text
rawX = (D0 << 4) | (D1 >> 4)
rawY = ((D1 & 0x0F) << 8) | D2
contact = (D6 & 0x80) != 0
screenX = trunc(rawX × 0.12515 × 800 / 100)
screenY = 480 - trunc(rawY × 0.12515 × 480 / 100)
```

缩放来自该固件实现，不能替换为常见的 0…4095 线性缩放。`rawY=0` 可产生 `screenY=480`；该边界不能直接用作 480 行图像的数组下标。未知字节不应命名成压力或手势。CAN1 报文是否能从车辆 OBD 直接观测，未确认。

驱动将未接触→接触、接触中坐标改变、接触→释放分别转为 `WM_LBUTTONDOWN`、`WM_MOUSEMOVE`、`WM_LBUTTONUP`。释放使用最后接触坐标；相同坐标不重复发送 MOVE，三种消息的 wParam 均为 1。防抖门限为 0 或 150 ms，判断为距上次释放严格大于门限。黑屏模式可发送 `0x8001 / wParam=0x00CB0000` 黑屏取消事件，不能把它当作普通鼠标消息吞掉。

## TSD 接口边界

| DeviceIoControl | 参数及已确认行为 |
| --- | --- |
| `0x0022000C` | 输出 7 字节坐标缓存：`D0,D1,D2,D4,D5,(D6&0x80),0`；不是事件队列 |
| `0x00220018` | 输入单字节 1 时重新按固定标题查找并缓存 HWND；0 不等于清除或恢复绑定 |
| `0x0022001C` | 输入 0/1，选择 0/150 ms 防抖门限 |

ready 请求即便查不到窗口也可能报告成功；缓存接口也可能在没有有效缓存时报告成功及长度 7。API 返回成功不足以证明触摸送达，轮询缓存会漏掉轮询间隔内的完整手势。当前产品不采用改标题重绑定或缓存轮询；这些接口约束用于诊断和避免后续误用。

## 当前 HMI 桥接契约

HMI 内的钩子在原厂框架处理目标输入之前进入桥接，只接受当前 HMI 进程中标题匹配的窗口。驱动继续绑定原厂 HWND，不修改其标题。

桥接将原厂客户区坐标经 ClientToScreen 转为屏幕坐标，再由工作线程 ScreenToClient 转为 WinXPlay 客户区坐标，投递标准鼠标消息。协议侧按实际视频区域映射坐标，黑边不触发点击。桥接不向其他系统窗口广播输入，不调用 SendInput。

整次按下、移动、释放保持同一归属；切换等待已按下的触点和按键释放。返回、投递失败或目标失效时取消输入，未结束手势进入丢弃状态，不能把剩余半个手势转给另一界面。内部代次只过滤过期排队消息，不是接收端私有协议。

按键仅转发白名单标准虚拟键：方向、Enter、Home、Backspace、Space、F6…F8 和媒体键 `0xB0…0xB3`。原厂音量、静音、倒车、电源、触屏故障及黑屏取消等其他消息保留原流程。

面板和方向盘原始输入都通过 `0x8000` 消息进入 HMI，wParam 为原始编号；普通按键的 lParam 为动作，旋钮/步进输入则是有符号步数。例如 BAND 原始编号 `0x03` 映射 HMI 事件 `0x0A`，两者都不是标准虚拟键或 CAN ID。

新增的原始输入适配仅在 CarPlay 活跃时转发，原厂前台时保留原处理。普通按键将 action=0 转为一组标准按下/释放，不猜测其他动作值的长按语义；曲目步进单独处理：

| 原始编号 | 原厂符号 | CarPlay 输入 |
| --- | --- | --- |
| 0x01 / 0x27 | FMUX_MODE / SWRC_MODE | Home（界面行为由 iPhone 决定；不强制循环地图/音乐 App） |
| 0x11 / 0x1E | FMUX_SEEK_UP / SWRC_SEEKUP | 下一首 |
| 0x10 / 0x1F | FMUX_SEEK_DOWN / SWRC_SEEKDOWN | 上一首 |
| 0x36 | SWRC_NEXT_PREV_PRESET_TRACK | 有符号 16 位步数；正数下一首，负数上一首，每步一次点击 |
| 0x34 | SWRC_AUDIO_SCROLL | 本车实测拨轮编号；同上，CarPlay 前台切歌，原厂前台透传 |
| 0x0D / 0x21 / 0x24 | 面板 OK / 方向盘滚轮 OK | 确认 |
| 0x0B / 0x25 | ESC | 返回 |
| 0x0E / 0x0F | 面板 UP / DOWN | 上/下导航 |

BAND 保持原来的 HMI/WinXPlay 交接；音量、静音不映射成媒体暂停。普通按键仅转换 action=0；步进输入不能按 action 处理。0x34/0x36 的零增量不发送事件，单条消息最多发送 16 次完整点击，投递失败立即停止。方向符号采用正数下一首、负数上一首的当前映射，实体拨动方向与正负号的对应仍待实测确认。

2026-10-12 首轮实车反馈：中控切歌正常，方向盘切歌无效；最初只补了原厂命名明确的 0x36，保留其他滚轮。后续 FILEOPS_0002 实车日志记录了 72 条拨轮事件，全部为十进制 52（0x34）：41 条 +1、31 条 -1，目标虚拟键全部为 0，没有 0x36 事件。这说明拨轮已到桥接入口，但映射遗漏；用户另确认原厂蓝牙播放可正常切歌。现将 0x34 同样映射成 CarPlay 上/下一首，原厂前台继续透传；0x32/0x33/0x35/0x37 仍保持原厂处理。此次修复尚待实车验证。

原始日志与哈希清单保存在根目录 evidence/vehicle/steering-wheel-fileops0002-20261012。典型旧日志：`[135655] RAW_STEP id delta virtual 52 1 0`、`[151384] RAW_STEP id delta virtual 52 -1 0`。修复后目标应分别为 176/177；日志中的目标编号仍不能单独证明手机已执行切歌。F3.21 的 0x01DD2488..0x01DD24AC 将旋钮语义事件分流，0x01DD25EC 对步数执行 SXTH，证据见根目录 evidence/analysis/input-can-20261008/disassembly/key-window-dispatch.txt。

调试版在桥接启动后记录目标 HMI 的全部 0x8000 原始输入，包括未映射编号。普通输入为 `RAW_KEY id action virtual`，已知旋钮范围 0x32..0x37 为 `RAW_STEP id delta virtual`；数字以十进制输出，delta 可为负，virtual=0 表示未映射。写盘在桥接工作线程进行。例：`RAW_STEP id delta virtual 54 -1 177` 表示 0x36、负一步、上一首。需分别在原厂界面及 CarPlay 内操作方向盘，回收 NAND_USER/WinXPlay/A_BRIDGE.log 核对，不能从旧版没有日志推断没有收到事件。

桥接 ARM 回归验证按键/步进映射、零增量、负数与批量步数、后台透传、未知事件日志和投递失败；共享核心回归验证 Home/媒体键进入加密事件通道。软件回归不等于新增方向盘分支已实车通过。MODE 对接 Home，手机内部页面行为仍由 iPhone 决定。
