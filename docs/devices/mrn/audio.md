# MRN 音频输出与采集

适用范围见 [MRN 设备说明](../mrn.md)。原厂接口结论来自 ENTAVMAIN、ENTSSIAUDIO、ENTSSIHFPAUDIO、ENTDICTAPHONEMAIN 及导航包装器的指令和注册配置核对。下文区分原厂契约、当前实现及实听范围，不以 API 成功替代出声或人声验收。

当前 MRN 默认关闭 CarPlay 音频输入和输出，保留 USB 画面与触控，声音使用原车蓝牙；下述音频后端仅在显式重新开启时使用。面向使用者的原因及限制见[MRN 使用提示与技术取舍](../../guides/mrn-usage-notes.md)。

## 输出设备与音源是两层接口

| 对象 | 已确认含义 |
| --- | --- |
| waveOut 设备 0，`Multi-channel Audio Output` | 原厂主媒体 ESAI 输出候选；完成 PCM 提交不保证扬声器可听 |
| waveOut 设备 1，`Audio Output` | 原厂语音合成选择的输出设备；当前 MRN PCM 后端采用它 |
| `entSSIAudio.dll` / 注册流设备 `WAV2:` | SSI 导航/语音驱动；流设备后缀不等于 waveOut 枚举编号 |
| `AVV0:` | 原厂音源协调接口，不直接接收 PCM 缓冲 |

枚举编号只对已验证的设备配置成立。打开设备、缓冲完成、驱动位置递增、原厂音源申请及扬声器出声是不同阶段。

## 当前采用的 TTS 输出契约

| 顺序 | 接口与行为 |
| --- | --- |
| 申请 | 打开 `AVV0:`，发送 IOCTL `0x33`，输入单字节 `0x04` |
| 等待 | 可取消地等待 2000 ms；这是稳定等待，不是异步激活确认 |
| 播放 | waveOut 设备 1，PCM16、48000 Hz、双声道；十个独立缓冲持续补充 |
| 清理 | 停止提交，重置并取消准备音频缓冲，关闭 waveOut |
| 释放 | 向 `AVV0:` 发送 IOCTL `0x34`，输入单字节 `0x04`，关闭句柄 |

`0x04` 是该语音接口的源标识，不是输出设备号。原厂文本合成请求也在 AVV0 上，但不能把 PCM 当文本发送。当前路径保留原厂 AV 服务，不通过结束原厂进程获得音源。

SSI 驱动的启动条件是第六次 WODM_WRITE 才触发 Run；计数对象是提交次数，而非音频字节数或时长。一次大缓冲加 Pause/Restart 不能替代多次提交；该计数还属于驱动全局状态，不能推广成所有 waveOut 驱动的规则。

当前 [WinCE 共享输出实现](../../../carplay/platform/wince/wave_mixer.cpp)按 [MRN 音源与参数](../../../carplay/devices/mrn/audio_route.cpp)使用十个独立 WAVEHDR，每个 4800 帧（48 kHz 下 100 ms），不使用 Pause/Restart 启动。多个逻辑流共用一个输出流，避免重复打开 SSI。每个逻辑流通过[有界 PCM 队列](../../../carplay/platform/common/pcm_queue.h)转换为 48 kHz 双声道；队列满时丢弃过期帧，混合结果做整数限幅。若驱动未释放缓冲，保留内存与错误状态，不释放仍可能被驱动访问的存储。

## 实听结论与未解决的仲裁

设备 1、TTS 申请、多缓冲的组合已有指定 MRN 上可听 PCM 及与原音源并行出声的记录，支持当前后端选择。它不证明任意源组合均能混音，也未确定混音发生的硬件环节。

完整音乐播放仍需验证原音源静音/保留、左右声道、长期稳定性、音量恢复和通话优先级。释放请求成功不等于原音源或音量已恢复。`physical_audio_verified`、`source_connection_verified` 保持为 false 的诊断字段不能擅自改成物理成功。

2026-10-12 的同会话蓝牙对照中，用户报告切换蓝牙音频后视频明显改善、蓝牙音质更好。归档 `build/validation/vehicle-20261012-bluetooth-comparison` 中，pid 220135478 在 tick 312954 释放 TTS 源，此后普通音频处理耗时归零，视频继续接收。稳定 TTS 播放区间的逐窗口音频处理耗时中位数为 79 ms，单包最大 173 ms；这是包含等锁/线程抢占的墙钟耗时，不能当作纯 CPU 时间，也不能排除 USB 共享资源。前后页面操作不同，不能将接收消息数差值当作受控显示帧率提升。当前 TTS 路线只有出声依据，尚不能证明音乐音质等同于原厂蓝牙路线，更不能凭此推定具体频响或 DSP 设置。

单路音频现在整块读取软件环形队列，避免在队列锁内逐帧遍历八个混音槽；多路仍混音并限幅，缓冲数量和大小不变。解密、队列锁等待、转换入队、填缓冲及驱动提交分别记录耗时，以区分后续阻塞来源。软件优化不代表 TTS 路线的物理音质问题已解决。

原厂 USB 文件媒体源的业务编号 `0x0A` 映射连接管理源 `0x0E`，并涉及可用性、预激活、激活和暂停/恢复回应。发一次“选择 USB”不会自动把独立 waveOut 流接入原厂播放器。该路线没有作为当前接收端输出实现，不应替换上述 TTS 契约。

## 麦克风：已知接口与实验边界

### 2026-10-12 主程序可双向通话，但有回声和自动生成备忘录缺陷

用户实测确认“音频输入有了，通话正常”，随后确认每次采集会在原厂语音备忘录中留下录音，回放能听到通话双方。此为用户实听反馈，本轮尚未取得对应录音文件或采集日志，也未核对运行 EXE 哈希；不能把双方可听直接认定为硬件混音，对端声音也可能经扬声器被麦克风拾取。

后续用户补充“对方说有回音”，因此“通话正常”只能保留为早期反馈；最新结论为上下行已经可听，但远端回声存在，通话质量未通过。当前 `audio_input.cpp`/`pcm_input.h` 仅采集、重采样、分包，没有软件 AEC，也没有向 AEC 提供下行播放参考。原厂 ENTSSIHFPAUDIO 的固件证据包含 ConfigECNR_Ex、StartECNR、VSP_audioControl(vsp_tx/vsp_rx) 和独立 HFP 采集路径，但这不能证明当前录音机采集与 TTS 播放已接入该处理链。须分别验证声学回录与内部回送，不能直接断定回声全部来自某一种路径；不能用降低麦克风增益或讲话时静音播放代替全双工回声消除。

当前实现的 AVV0 IOCTL 4 / `10 01`、IOCTL 1 / `10` 复用了原厂录音机业务的选择流程，并非已经隔离的纯麦克风路由。WinXPlay 的 `audio_input.cpp` 只取 PCM 并上传，没有创建 WMA 备忘录的代码。原厂 ENTDICTAPHONEMAIN `0x100209DC` 接收 SourceActivity 后向状态机投递事件；`0x1001E744` 的 StartRecord 经 `0x1000DE98` 发起原厂录制。其 `__hndStartRecord` 在 `0x1000ED90..0x1000EDDC` 拼接 `\NAND_USER\entDictaphone\` 和时间戳 `.wma` 文件名，并在 `0x1000EED8` 调用原厂录制流程。现有实测与这条业务副作用相符，但本轮未动态抓取完整激活回调链。

验证状态应为“电话上下行可听；远端有回声；自动生成含通话内容的原厂录音，两个缺陷未解决”，不能标记整个麦克风方案验收完成。后续需把麦克风硬件/路由开启与备忘录业务启动分离，并核实原厂 ECNR 能否接收本程序上下行；否则需要以实际播放 PCM 为参考的软件 AEC 及延迟对齐验证。不能仅删除源申请（既有基线会全零），也不能把删除生成的录音文件当作修复。现有备忘录不自动删除。尚未发布消除此副作用或回声的新二进制。

原厂语音识别采用 PCM16、16 kHz、单声道；录音机业务采用 PCM16、22050 Hz、单声道。ENTSSIHFPAUDIO 中两种采样率进入不同 DMA 启动分支，其他采样率的格式查询成功不代表能从空闲状态开始采集。录音机的 22.05 kHz 业务格式不能因驱动内部状态出现 44.1 kHz 就自行改写。

当前独立录音测试复刻的请求顺序为：

| 阶段 | AVV0 IOCTL | 输入字节（十六进制） |
| --- | --- | --- |
| 标记录音机源可用 | `4` | `10 01` |
| 选择 | `1` | `10` |
| 标记不可用 | `4` | `10 00` |
| 取消选择 | `2` | `10` |

请求由[录音源适配](../../../carplay/tools/mrn/microphone_route.h)实现，操作步骤见[诊断工具](../../../carplay/tools/mrn/README.md)。测试选 waveIn 设备 0，不把 waveOut 设备 1 或 `WAV3:` 后缀作为输入编号；waveIn 0 到具体流驱动的运行时映射尚未直接确认。

2026-10-12 实车测试 `microphone-2` 已确认：未申请音源的 22050 Hz 基线录制 6 秒但全零；申请源 0x10 后，同格式录制 6 秒、264600 字节 PCM，用户回听 `dictaphone-22k-device-0-22050hz-1ch.wav` 明确确认正常说话声音。独立 WAV 解析与日志一致，四个音源请求及 waveIn 清理均成功。16 kHz 基线只在前 2 秒内有非零样本，后续全零，不能视作稳定采集通过。原始证据归档在研究工作区 `evidence/vehicle/microphone-v4-20261012`。

因此，本机已验证的独立采集组合是 **录音机源 0x10 + waveIn 设备 0 + PCM16 / 22050 Hz / 单声道**。该组合现已接入[主程序 MRN 采集后端](../../../carplay/devices/mrn/audio_input.cpp)：手机请求后申请音源，poll 在 2000 ms 等待期间返回空包，让接收循环继续处理视频/控制；随后打开设备并提交八个 100 ms 缓冲。带跨缓冲状态的线性重采样转换至手机协商的采样率，按 framesPerPacket 精确分包，沿现有加密 UDP 上行发送。流结束/异常时重置、关闭并释放源；清理失败保留驱动缓冲并阻止本进程再次打开。Generic 仍使用标准 wave 输入，不发送 MRN 请求。

主程序接入已做桌面 API 替身测试（七种采样率连续性/分包、等待阶段、独占、失败清理）及共享核心加密上行回归；后续用户确认通话正常，但发现同步生成备忘录，见上方缺陷记录。线性重采样不含专门语音降噪或回声消除；通话正常不代表回声消除和长时稳定性已验收。原厂源归属仍无法查询，且现在已有原厂录音业务并行启动的实测反馈。

同日再次测试 `microphone-1`，用户再次确认只有申请音源的 22.05 kHz 录音可听；日志和报告显示两段未申请音源的 16 kHz / 22.05 kHz PCM 均全零。有效段字节数对应 6 秒，峰值 6090，131871 个非零样本，音源申请/释放和采集清理均成功。读取日志后 E 盘断开，尚未归档本轮原始 WAV/EXE，也未独立解析 WAV；读取摘要保存在同一证据目录的 `retest` 子目录。未提供冷启动条件，也未因此扩大为长期稳定性验证。

录音源实验没有完整的异步激活确认或原会话归属查询，只能在原厂录音、语音识别、电话及接收端采集空闲时运行。释放后恢复、CarPlay 上行、Siri、全双工回声消除和长时稳定性仍待验证。用户的具体文件回听确认与原始报告分开保存，不修改程序固定的 voice_verified 字段。

## 维护和回归入口

2026-10-12 加入普通 AAC-LC：设备只选择原厂 `AACDMO.DLL` CLSID `{37CA27C5-5E4E-4F0C-8DCF-FEC2B5EB789F}`；WinCE 平台通过标准 `IMediaObject` 接口解码。原厂输入格式检查的 ARM 指令验证接受 0x1600 ADTS、44.1/48 kHz 双声道，拒绝 0xff RAW_AAC1；手机的 raw AAC access unit 在平台层补 ADTS 头。启动时在独立 COM 线程解码四个静音包，产生 PCM 才声明普通 AAC，失败保留 PCM。运行解码线程的压缩队列最多 24 包，溢出舍弃最旧待解码包并 Flush；不等同于原有 PCM 队列。普通 PCM 路径及 TTS 路由未改，不能据此宣称音乐音质已改善。

`DeviceProfile.audio.output/input` 默认为 true，可通过 `carplay.plist` 的字符串 `CARPLAY_AUDIO_OUTPUT` / `CARPLAY_MICROPHONE` 独立覆盖。两项关闭时不声明音频、不打开音频设备；只关闭输出仍可声明单声道上行，是否与手机蓝牙路由共存需实车确认。开关不负责原车蓝牙连接。当前 MRN 发布默认关闭两路音频，保留视频和触控；平台默认仍为开启。运行配置若显式设为字符串 1，会覆盖设备默认值。修改配置后重新启动接收端和建立会话。

AAC 主机适配器测试覆盖 ADTS 封装、COM 引用生命周期、解码线程、队列溢出、暂停及失败清理；原厂 ARM 检查只证明格式契约，自检及实车结果另行记录。`carplay/scripts/test-ce-aac.ps1` 是开发测试入口，不需要用户部署额外测试程序。

后续实车日志确认 AAC 启动解码自检通过，并向手机声明普通 AAC；但同轮 212 条音频统计记录均为 PCM16，未观察到 AAC 音乐流。因此自检通过只证明该设备能解码自检素材，不能报告 AAC 音乐或性能改善已验收，也不能推定手机优先选择 AAC。

输出后端选择位于 [MRN 装配](../../../carplay/devices/mrn/wince.cpp)，退避重开策略位于 [audio_recovery.cpp](../../../carplay/platform/wince/audio_recovery.cpp)。平台注册入口只委托设备选择，Generic 使用标准 wave，不启用 MRN TTS。[MRN 输出测试](../../../carplay/tests/wince/mrn_audio_test.cpp)、[PCM 测试](../../../tests/test_voice_pcm.py)及[有限播放检查](../../../tests/test_tts_pcm_finite.py)覆盖相应软件行为。上述回归不提供真实音源仲裁或声学测量；物理能力以[兼容性表](../../compatibility.md)为准。
